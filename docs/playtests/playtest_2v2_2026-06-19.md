## ISSUE-01 fix validation — ⚠️ PARTIAL: infinite loop gone, but research throughput still regressing vs vanilla (specifically WatchTower)

**Commit `1512b3b`** (removed 15 broken force-research branches from `haveForcedEconomicTechnologyToResearch` in `core/techs.xs`) successfully stopped the infinite trap loop. However, follow-up review by the user revealed that **research throughput is still below vanilla** for at least one critical case (P4 Atlantean).

### What IS verified working

- **Zero infinite traps on the economy side** — `economyUpgradeManager` runs clean research chains (Pickaxe→HandAxe, etc.) across both AIs and the full game duration.
- **No 30s cycling** — the old trap message (`Not running through the default logic because we have a forced technology`) only fires when a forced tech plan actually enters `cPlanStateResearch` afterward.
- **Watchdog fires correctly** on genuinely stuck plans (HeavyCavalry #283, HeavyArchers #396, LevyPalaceSoldiers #593) — each destroyed cleanly after 2 min, no loop.
- **Fix held through endgame collapse** — P3's final 6 minutes showed the watchdog firing once cleanly on plan #576 → recreated #681, no looping despite catastrophic state (militaryPop 0/3, economyPop 4/101).

### Important context (user correction)

**Vanilla AI enforces "one research globally at a time"**: even with multiple buildings (Armory, Market, Dock, Temple) able to research different upgrades simultaneously, vanilla only allows ONE active research plan at any time. This vanilla behavior carried into the mod.

**For Freyr (P3) this means slow military research is VANILLA behavior, not a mod regression**: Freyr's unique passive makes all techs cost 50% but take 250% research time. With vanilla's one-research-slot rule, Freyr effectively needs 2.5× the usual game time to research the same techs — Freyr AI is structurally disadvantaged in vanilla. **P3 was a red herring** — the user has confirmed they only noticed the slowness now because they were specifically watching it; it has always been there.

### What is STILL BROKEN — WatchTower never researched (P4 Atlantean)

**The clearest mod-side regression**: P4 NEVER researched WatchTower (the upgrade that makes SentryTowers actually attack). Yet:
- Armory completed at 00:09:34 (well before the 4-min-Classical gate is supposed to trip)
- P4 reached Classical at 00:04:03 → 4 min later = 00:08:03 (gate should have fired)
- P4 reached `gDefensivelyOverrun = true` multiple times from 00:17:23 onward (which should trigger defensive WatchTower cast per the mod's rewrite)
- P4 reached Mythic Age at 00:19:11 (the "always research if age >= cAge3" fallback should have fired)
- Multiple SentryTowers were built throughout the game (#95 at 00:09:34, #240 at 00:15:39, #309 at 00:17:39, #453 at 00:20:28, etc.) — **all useless without WatchTower**

**Vanilla AI does not skip WatchTower for long** — the user confirmed they've never seen vanilla AI ignore the WatchTower research.

### Prime suspect — mod's rewrite of `towerOffensiveUpgradeMonitor` (in `techs.xs`)

The diff agent (`inland-gold-hippopotamus`) reported the mod rewrote `towerOffensiveUpgradeMonitor`:
- Removed the `firstTowerUpgrade`/`secondTowerUpgrade`/Aztec `TemiminaloyanTrials` variable indirection.
- Added direct `cTechWatchTower`/`cTechTzompantliWatchTower`/`cTechBoilingOil`/`cTechTemiminaloyanTrials`/`cTechGuardTower` branches.
- The new WatchTower branch gates on `time < xsGetTime()` where `time = gAgeUpTimes[cAge2] + 240` (or −60 for Defender), or `gDefensivelyOverrun == true`, or `age >= cAge3`.

**Critical clue**: This gate uses `xsGetTime()` — the SAME function that drives the `ISSUE-NEW-2` wall-rule "time < 8 min" canary which is incorrectly firing at game minute 20+. Either:
1. `xsGetTime()` returns something different than expected in Retold (perhaps not game-clock milliseconds).
2. There's an operator-precedence or typing bug in the comparison.
3. The modded condition is OK on paper but `gAgeUpTimes[cAge2]` is being set incorrectly, suggesting a much later time.

Either way — the mod broke both the wall time gate (ISSUE-NEW-2) AND the WatchTower time gate with the same `xsGetTime()`-based comparison code. They're likely the same bug. **Fixing one will likely fix both.**

### 🔴 ISSUE-NEW-1: WatchTower research never fires (HIGH — mod-side regression, confirmed by user)

**Symptom (Player 4 Atlantean, P4)**: Despite completing an Armory at 00:09:34, reaching Classical at 00:04:03, reaching Mythic at 00:19:11, and crossing `gDefensivelyOverrun = true` multiple times from 00:17:23 onward, **P4 NEVER researched WatchTower** — leaving every SentryTower it built (#95, #240, #309, #453, etc.) useless for combat.

**Vanilla AI does not skip WatchTower** — the user confirmed they've never seen this in vanilla. This is a mod-side regression.

**Root cause hypothesis**: The mod rewrote `towerOffensiveUpgradeMonitor` (in `core/techs.xs` lines ~1880-1980), replacing the base's `firstTowerUpgrade`/`secondTowerUpgrade` variable indirection with direct `cTechWatchTower`/`cTechTzompantliWatchTower` branches using a new time-gated condition:

```xs
int time = gAgeUpTimes[cAge2] + 240;  // 4 min after Classical
if (cPersonalityCurrent == cPersonalityDefender) { time -= 60; }
if (time < xsGetTime()) { researchUpgrade = true; }
```

**Critical clue** — the gate uses `xsGetTime()`, the SAME function that drives ISSUE-NEW-2's wall-rule "WAITING: time < 8 min" canary which fires incorrectly every 10s even at game minute 20+. If `xsGetTime()` is returning an unexpected value in Retold, both the WatchTower time gate AND the wall time gate would be broken by the same root cause.

Cross-check: log timestamps show parenthesized values like `00:20:07 (1200700)` — the parens value appears to be `xsGetTime()` and equals ~1,200,700ms = 20 min. If that's correct, then `xsGetTime() < 8 * 60 * 1000` (480,000) should evaluate FALSE at minute 20+ — but the wall rule's canary is firing anyway. This means either:
1. The agent's reported diff for the gate is inaccurate (real condition is different).
2. Operator precedence or typing issue in XS's `<` operator.
3. `gAgeUpTimes[cAge2]` is returning a huge value, making `time` ALWAYS greater than `xsGetTime()` despite both being in the same unit.

**Fix needed**: 
1. Read the actual current code of `towerOffensiveUpgradeMonitor` in the mod — verify the agent's diff was accurate.
2. Add debug canaries to the WatchTower gate (similar to the wall rule): `debugTechs("--- towerOffensiveUpgradeMonitor ---")` at top, `debugTechs("WatchTower gate: time=" + time + " xsGetTime=" + xsGetTime())` at the gate. Then re-playtest.
3. Same investigation path applies to the wall rule's `xsGetTime()` gate (ISSUE-NEW-2) — they likely share the same root cause.

## Other notable behaviors (informational, no action needed)

### `cStateForcedCantAttack` lock during defense panic (matches prior ISSUE-09)

Both AIs spent large portions of their late game in `cStateForcedCantAttack` — the state set when `gDefensivelyOverrun == true`. This is the existing ISSUE-09 lock that was documented in the prior 1v1 playtest. The flag was set whenever enemy power > own power at any base, and typically cleared only after the threat dropped below threshold.

P3 entered this state at 00:20:59 (when AutoBase 111 was overrun) and remained there for the rest of the game (until resignation at 00:29:30). P4 first entered at 00:17:23, recovered briefly, re-entered at 00:19:26 (230 enemy power hit on AutoBase 24), recovered, re-entered again at 00:20:33, and remained in this state until resignation at 00:26:00.

This matches the prior playtest's finding exactly. As documented then, `military_defend.xs` (which manages the flag) is NOT currently overlaid by the mod — fixing it would require a new overlay file.

### Pre-Armory Ballistics pre-churn (working as designed)

Both AIs showed a brief window of ~5 min (P4) / 4.5 min (P3) of Ballistics plan IDs cycling through the destroy/recreate pattern. This happens because the AI tries to research Ballistics AS A FORCED TECH (the last-resort military upgrade path) BEFORE the Armory is built. The plan created has `needed = (0, 0, 0, 0)` resource requirements when there's no researcher slot available, so it can't enter `cPlanStateResearch`. The watchdog eventually destroys it; once Armory exists, the next plan correctly shows real needs and enters research state.

This is annoying log noise but not the ISSUE-01 trap. It's pre-existing base AI behavior. Could optionally be tightened by gating on Armory existence, but not a fix priority.

### `ageUpPriority` defensive suppression

During `gDefensivelyOverrun == true` periods, the AI correctly suppresses `ageUpPriority` to `48` instead of the standard `55` post-4-minute bump:
- P4 at 00:19:29: `"We're currently being defensively overrun, keep age up priority low until we deal with this threat."`

This is working as designed — it prevents wasteful age-up research during combat when resource extraction is needed elsewhere.

### `useUnusedGodPowersMonitor` aggressive auto-fire

The monitor auto-fired `AsgardianBastion` (P3), `Valor` (P4 — multiple times), `HesperidesTree` (P4) and `Vortex` (P4). The Vortex case is suboptimal — Vortex is situationally an emergency defensive power, not just a "use because we have a charge" power. The monitor lacks situational awareness.

### `enemyHeroPop` clamps `minimumMythPop` aggressively

When the AI scouted `enemyHeroPop: 81` (or similar large values), the AI chose to use `minimumMythPop` to cap its own myth pop target. This is correct defensive logic, but worth noting for understanding of why the AI sometimes underproduces myth units.
