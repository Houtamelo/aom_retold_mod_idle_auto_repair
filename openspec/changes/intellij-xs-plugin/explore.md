# SDD Explore — `intellij-xs-plugin`

**Goal:** Investigate and document the design space for an IntelliJ Platform plugin that ports the feature set of the VS Code XS extension (`extracted/xs.vsix` v1.1.1) to JetBrains IDEs (Rider + IntelliJ IDEA).

**Locked decisions (not re-litigated):**

- Target: IntelliJ Platform, plugin lives in `tools/intellij-xs-plugin/`.
- Scope: full feature parity with the VS Code extension's six capability families.
- Distribution: deferred until the plugin is functional end-to-end.
- Sequencing: cheap-first 80 % (TextMate grammar + syscalls completion/hover), expensive-last 20 % (real XS PSI, references, classes, lambdas).

**Executive summary**

Porting the VS Code XS extension to IntelliJ is straightforward for the engine-facing features and harder for code intelligence features. We already own all the engine data: `syscalls.json` (1,805 entries) and `aiplans.json` (193 entries), both derived from `docs/doxygen_retail/`. The TextMate grammar (`syntaxes/xs.json`) can be reused through IntelliJ's bundled TextMate plugin, giving us syntax highlighting in hours. Completion, hover, and parameter info for engine syscalls can be built textually from the JSON with no XS parser. The expensive work is faithfully reproducing the VS Code extension's workspace-level code intelligence (go-to-definition, class member completion, lambda parsing), which needs a real PSI tree. This explore doc recommends a staged delivery: bundle the grammar first, then load syscalls for completion/hover, then build a parser incrementally, and only at the end tackle XML-derived constants and a doxygen-to-JSON regeneration pipeline.

## 1. Source-of-truth inventory

### 1.1 `syscalls.json` — the engine API

File: `extracted/xs.vsix/extension/syscalls/syscalls.json` (1.16 MB, v1.1.1).

- **Entries:** 1,805 syscalls.
- **JSON shape:**
  ```json
  {
    "syscalls": [
      {
        "name": "aiAddEchoCategory",
        "help": "Adds a category ...",
        "return_type": "int",
        "params": [
          { "type": "string", "name": "categoryName", "default": "\"Invalid Category\"" }
        ],
        "filename": "aifuncs.cpp"
      }
    ]
  }
  ```
- **Distribution by source file:**

  | `filename` | Count | Relevant doxygen page |
  |------------|-------|-----------------------|
  | `aifuncs.cpp` | 215 | `docs/doxygen_retail/aifuncs_8cpp.html` |
  | `kbfuncs.cpp` | 423 | `docs/doxygen_retail/kbfuncs_8cpp.html` |
  | `kbarmyfuncs.cpp` | 23 | `docs/doxygen_retail/kbarmyfuncs_8cpp.html` |
  | `kbprogressionfuncs.cpp` | 6 | `docs/doxygen_retail/kbprogressionfuncs_8cpp.html` |
  | `kbtechtreefuncs.cpp` | 32 | `docs/doxygen_retail/kbtechtreefuncs_8cpp.html` |
  | `randommapfuncs.cpp` | 502 | `docs/doxygen_retail/randommapfuncs_8cpp.html` |
  | `triggerfuncs.cpp` | 408 | `docs/doxygen_retail/triggerfuncs_8cpp.html` |
  | `triggerfuncs_mainthread.cpp` | 105 | `docs/doxygen_retail/triggerfuncs__mainthread_8cpp.html` |
  | `xsfuncs.cpp` | 91 | `docs/doxygen_retail/xsfuncs_8cpp.html` |

`syscalls.json` is almost certainly a cleaned extract of the doxygen crawl: same function names, same parameter lists, same descriptions. It is the *bundled* source of truth the plugin should ship with.

### 1.2 `docs/doxygen_retail/` — the upstream API crawl

Generated by Doxygen 1.15.0 against the "ATHENS SYSCALLS" engine sources. 51 HTML files.

**Most useful pages for the plugin:**

- `xsfuncs_8cpp.html` — XS language functions (`xsEnableRule`, `xsDisableSelf`, `xsSetRulePriority`, etc.).
- `aifuncs_8cpp.html` — AI planning/utility syscalls.
- `kbfuncs_8cpp.html` — Knowledge-base queries, the largest single file.
- `randommapfuncs_8cpp.html` — Random-map scripting syscalls.
- `triggerfuncs_8cpp.html` and `triggerfuncs__mainthread_8cpp.html` — Trigger engine syscalls.
- `kbarmyfuncs_8cpp.html`, `kbprogressionfuncs_8cpp.html`, `kbtechtreefuncs_8cpp.html` — Smaller KB sub-domains.
- `aiplans_8cpp.html` — AI plan constants source (number-to-name plan variables).
- `globals_*.html` and `globals_func_*.html` — Prefix/file cross-indices; useful for validation, not for primary extraction.
- `index.html` and `doxygen_crawl.html` — Entry points for navigation.

**Machine-readable structure (used by the regeneration pipeline):**

- Function name: `<td class="memname">int aiAddEchoCategory </td>`.
- Return type: preceding `<td class="memItemLeft" align="right" valign="top">int </td>`.
- Parameters: pairs of `<td class="paramtype">string</td>` and `<td class="paramname"><em>categoryName</em></td>`.
- Default values: `<table class="params">` rows like `<tr><td class="paramname">categoryName</td><td>default value: "Invalid Category" </td></tr>`.
- Description: the first `<p>` inside `<div class="memdoc">` (or `<div class="textblock">`).

### 1.3 XML-derived constants — user-supplied game data

The VS Code extension reads five AoM:R XML files through settings keys:

- `xs.protoXml`
- `xs.techtreeXml`
- `xs.civsXml`
- `xs.culturesXml`
- `xs.powersXml`

These are relative paths inside the workspace. The actual game files are typically inside `data/Data.bar` (the main game asset archive) and must be extracted by the user before the plugin can read them. Modding practice also allows additive override files `*_mods.xml`.

| Setting key | Game file (in `.bar`) | Likely root | Entry tag | Name source | Also emitted from | Constant prefix |
|-------------|----------------------|-------------|-----------|-------------|-------------------|-----------------|
| `xs.protoXml` | `proto.xml` | `<proto>` (or additive `<protomods>`) | `<unit name="...">` | `@_name` attribute | any child `<UnitType>` text | `cUnitType{Name}` |
| `xs.techtreeXml` | `techtree.xml` | `<techtree>` (or additive `<techtreemods>`) | `<tech name="...">` | `@_name` attribute | — | `cTech{Name}` |
| `xs.civsXml` | `civs.xml` | `<civs>` | `<civ>` | child `<Name>` text | — | `cCiv{Name}` |
| `xs.culturesXml` | `cultures.xml` | `<cultures>` | `<culture>` | child `<Name>` text | — | `cCulture{Name}` |
| `xs.powersXml` | `powers.xml` | `<powers>` | `<power name="...">` | `@_name` attribute | — | `cProtoPower{Name}` |

Implementation caveat from the existing extension: XML parsing is case-insensitive for attribute/child names (it normalizes `@_name` and `Name`). The parser must tolerate the fact that some entries may be objects and some arrays when a file has one versus many children. Any `<UnitType>` child of a `<unit>` is also emitted as a `cUnitType` constant.

### 1.4 `constants/aiplans.json` — bundled AI plan constants

- **Entries:** 193 constants.
- **JSON shape:**
  ```json
  {
    "constants": [
      {
        "name": "cAttackPlanAttackRouteID",
        "value": 0,
        "variable_type": "int",
        "variable_value": "-1"
      }
    ]
  }
  ```
These are the plan-variable constants used by `aiPlanGetVariableInt`-style APIs. They can be loaded the same way as syscalls and contributed as `LookupElementBuilder` items.

### 1.5 TextMate grammar — understanding declarations

File: `extracted/xs.vsix/extension/syntaxes/xs.json` (1,626 lines, derived from `jeff-hykin/cpp-textmate-grammar`).

**Rule declarations (repository section):**

```json
"rule_definition": {
  "patterns": [
    {
      "match": "(?-mix:(?<!\\w)(?:rule)(?!\\w))\\s+(?x)(?!(?:while|do|for|if|else|switch|return)\\s*\\()((?:[A-Za-z_][A-Za-z0-9_]*+)++)(?!\\s*\\()",
      "name": "storage.type.built-in.primitive.c",
      "captures": {
        "1": { "name": "entity.name.function.c" }
      }
    }
  ]
}
```

This gives us the lexical shape of a rule for free: `rule <name>` where `<name>` is a normal identifier and must not be followed by `(`.

The grammar also encodes three important XS naming conventions via simple regex scopes:

- `\bk[A-Z]\w*\b` → constants (`k...`).
- `\bg[A-Z]\w*\b` → globals (`g...`).
- `\bs[A-Z]\w*\b` → statics (`s...`).

These are *conventions*, not enforced by the XS engine; when we build a PSI later we should not treat them as syntax rules.

## 2. Capability decomposition

The VS Code extension grows across six feature families. For each family we list: user-facing behavior, the IntelliJ extension point, whether a real XS parser (PSI) is needed, and a rough effort estimate.

### 2.1 Engine syscall auto-completion and parameter completion

**What the user sees:**

- Typing `aiPla` proposes `aiPlanCreate`, `aiPlanAddUnitType`, etc.
- Typing `aiPlanCreate(` proposes the first parameter's default value.
- Typing `,` inside the call proposes the next parameter's default value.

**IntelliJ extension points:**

- `com.intellij.completion.contributor` → `CompletionContributor` for the name list.
- The same contributor can respond to `(` and `,` trigger characters by injecting parameter-value lookup items.

**Needs PSI?** No. Syscalls can be looked up by name from `syscalls.json`.

**Effort:** 1–2 days. Main blockers are loading the bundled JSON and building performant `LookupElementBuilder` items (pre-build ~1,805 items once at load time).

### 2.2 Workspace symbol completion

**What the user sees:**

- Typing `disableAuto` proposes the user-defined `disableAutoScouting` function.
- Typing after a known class variable and `.` proposes class members and methods.
- Rules (`rule cleanupLingeringExplorePlans`) appear alongside functions.

**IntelliJ extension points:**

- `CompletionContributor` using textual regex for Phase 1.
- `PsiReference.getVariants()` once we have a PSI.

**Needs PSI?** Textual regex can cover top-level functions/rules/variables (the VS Code extension does exactly this). Class-member completion and lambdas definitely need PSI or a very fragile regex engine.

**Effort:** 1–2 days for top-level workspace symbols; 3–5 days for members/lambdas with PSI.

### 2.3 Hover documentation

**What the user sees:**

- Hovering over `aiPlanCreate` shows `int aiPlanCreate(string planName = "", int type = -1)` plus the help paragraph.
- Hovering over a user function shows its declaration.

**IntelliJ extension point:**

- `com.intellij.lang.documentationProvider` → `DocumentationProvider`.

**Needs PSI?** Syscalls need only name matching. User symbols benefit from PSI but can use regex descriptors for the first cut.

**Effort:** 1 day for syscalls; 2–3 days for parser-backed symbols.

### 2.4 Go-to definition / references

**What the user sees:**

- `Ctrl+B` on a syscall name jumps to its definition in `syscalls.json` or shows a generated stub.
- `Ctrl+B` on a workspace function/rule/variable/class/member/method jumps to its declaration.
- Find usages works across the workspace.

**IntelliJ extension points:**

- `com.intellij.psi.referenceContributor` → `PsiReferenceContributor` / `PsiReferenceProvider`.
- Optional: `com.intellij.gotoDeclarationHandler` for non-PSI text ranges.
- Optional: `com.intellij.findUsagesProvider` for find usages.

**Needs PSI?** Yes for reliable workspace resolution, class scopes, and member resolution. Textual regex can fake go-to-definition for simple top-level identifiers but will break on shadowing, class scopes, lambdas, and overloaded method names.

**Effort:** 3–5 days for top-level identifiers; 2–3 weeks for classes, members, and lambdas.

### 2.5 Parameter highlight / parameter info

**What the user sees:**

- When the caret is inside a call, a popup shows the signature and bolds the current parameter.

**IntelliJ extension point:**

- `com.intellij.codeInsight.parameterInfo` → `ParameterInfoHandler` (or `ParameterInfoHandlerWithTabActionSupport`).

**Needs PSI?** No for syscalls: determine the call site by scanning back for an identifier before `(`, then index the comma count into the JSON parameter list. With PSI, the same handler becomes trivially robust for workspace calls.

**Effort:** 1 day for syscalls; 2–3 days for workspace calls once PSI exists.

### 2.6 Syntax highlighting

**What the user sees:**

- Keywords, types, comments, strings, numbers, rule names, and `k`/`g`/`s` prefixes are colored.

**IntelliJ extension point:**

- `com.intellij.textmate.bundleProvider` → `TextMateBundleProvider` (preferred, reuses the VS Code grammar verbatim).
- Alternative: `com.intellij.lang.syntaxHighlighterFactory` + custom `SyntaxHighlighter`.

**Needs PSI?** No.

**Effort:** Hours if we bundle the existing TextMate grammar; 3–5 days if we implement a custom lexer/highlighter.

### 2.7 XML-derived constants + AI plan constants

**What the user sees:**

- Typing `cUnitType` proposes `cUnitTypeVillagerGreek`, etc., generated from `proto.xml`.
- Typing `cTech`/`cCiv`/`cCulture`/`cProtoPower` similarly proposes XML-derived names.
- Typing `cPlan` proposes constants from `aiplans.json`.

**IntelliJ extension points:**

- `CompletionContributor`.
- `com.intellij.applicationConfigurable` or `com.intellij.projectConfigurable` for a settings page to set the five XML paths.

**Needs PSI?** No.

**Effort:** 2–4 days, mostly spent on settings UI, file watching, XML parsing, and keeping the generated constants up to date when the XML files change.

## 3. Parser strategy options

XS is C-like with functions, rules, variables, classes, methods, lambdas, `ref`, arrays, `extern const`, `mutable`, and `include`. The right parser strategy determines the feature ceiling.

| Strategy | How it works | Pros | Cons | Capability ceiling |
|----------|--------------|------|------|--------------------|
| **A. TextMate grammar only** | Ship `syntaxes/xs.json` through a `TextMateBundleProvider`. | Zero parser code; full reuse of existing grammar; syntax highlighting in hours. | No code model at all; references/completion are textual and fragile. | Syntax highlighting; textual completion/hover for syscalls; regex-based workspace completion. |
| **B. GrammarKit + BNF grammar** | Write `xs.bnf` and a JFlex lexer; let GrammarKit generate the parser. | Generates PSI for free; idiomatic IntelliJ; good IDE support. | C-like expression/operator precedence, lambdas, `ref`, and arrays make the BNF large; error recovery may be poor if grammar is ambiguous. | Full PSI, references, refactoring, inspections — assuming the grammar can be made to fit. |
| **C. Hand-rolled recursive-descent parser** | Implement `XsParser` that reads tokens and builds a PSI tree manually. | Full control over XS-specific quirks; can mirror the regex assumptions in `extension.js`; easier to recover from errors incrementally. | More code to write and maintain; must update when XS syntax changes. | Full PSI plus custom recoverability; recommended if GrammarKit struggles. |
| **D. JFlex lexer + manual PSI builder** | Generate only the lexer with JFlex; write a `ParserDefinition` that creates PSI nodes by hand. | Avoids BNF complexity; explicit PSI shape; good middle ground. | Same hand-written parser effort as C, minus lexer bookkeeping. | Full PSI; good if we only need light structure (declarations, calls, classes) and not a full expression parser. |

**Recommendation:**

- Start with **A** for Phase 0/1 (syntax highlighting + syscall intelligence without a parser).
- For Phase 2/3, try **B** first because it is the canonical IntelliJ approach. If lambdas, `ref` arrays, or expression parsing become unwieldy, downgrade to **C** or **D** for the parts that are painful. A hand-rolled parser is the safest fallback because we already have the VS Code extension's regex grammar as a reference model.

## 5. Regeneration pipeline

`s syscalls.json` will drift when the game updates. We should own a small generator that re-derives it from `docs/doxygen_retail/*.html`.

**Outline of a generator (Kotlin + jsoup, or a Gradle task):**

```kotlin
fun regenerateSyscalls(
    doxygenDir: Path,
    outFile: Path
) {
    val files = mapOf(
        "aifuncs_8cpp.html" to "aifuncs.cpp",
        "kbfuncs_8cpp.html" to "kbfuncs.cpp",
        // ... all 9 source files
    )

    val syscalls = files.flatMap { (htmlName, cppName) ->
        val doc = Jsoup.parse(doxygenDir.resolve(htmlName).toFile())
        doc.select("div.memitem").map { item ->
            val name = item.selectFirst("td.memname")?.text()?.trim()
                ?.removePrefix("virtual ")?.removeSuffix(" ") ?: return@map null
            val returnType = item.selectFirst("td.memItemLeft")?.text()?.trim() ?: "void"
            val params = item.select("table.params tr").mapNotNull { row ->
                val pName = row.selectFirst("td.paramname")?.text() ?: return@mapNotNull null
                val pType = row.selectFirst("td.paramtype")?.text() ?: "?"
                val default = row.select("td").getOrNull(1)?.text()
                    ?.removePrefix("default value:")?.trim() ?: ""
                SyscallParam(pType, pName, default)
            }
            val help = item.selectFirst("div.memdoc p")?.text()?.trim() ?: ""
            Syscall(name, help, returnType, params, cppName)
        }.filterNotNull()
    }

    outFile.writeText(
        Json.encodeToString(SyscallFile(syscalls)),
        Charsets.UTF_8
    )
}
```

**Key considerations:**

- Doxygen emits `void` returns and array types such as `float[]`; preserve them exactly as they appear.
- Default values are plain text. The current `syscalls.json` stores them as XS literal text (e.g., `"\"Invalid Category\""`, `"-1"`, `"true"`). The generator should convert doxygen default text to the same escaped JSON string form.
- Some functions have overloads. The current `syscalls.json` appears to have one entry per name; if doxygen produces overloads, decide whether to merge or pick the most useful. Start by preserving one entry per unique name and discarding duplicates.
- The pipeline should be a committed Gradle task (`./gradlew regenerateSyscalls`) or a small CLI in `tools/intellij-xs-plugin/`. It runs against the local `docs/doxygen_retail/` copy.

## 6. Test & verification strategy

This repo has no automated XS runner, but the plugin itself can be tested with IntelliJ's standard `testFramework`.

**Minimum viable test setup:**

1. Add `testFramework(TestFrameworkType.Platform)` in Gradle.
2. Add fixture files under `src/test/testData/`:
   - `human_assist.xs` — a copy of `mod/intelligent_auto_repair_and_scout/game/ai/human_assist/human_assist.xs`.
   - `minimal.xs` — a hand-written file with a function, a rule, a variable, a class, a lambda, and a class method.
3. Write one `LightPlatformCodeInsightFixtureTestCase` per feature family:
   - `XsSyscallCompletionTest` — assert `aiPlanCreate` appears and `aiPlanCreate(` inserts the first default parameter.
   - `XsHoverTest` — assert the generated doc contains the syscall signature.
   - `XsParameterInfoTest` — assert the parameter popup shows the correct index.
   - `XsWorkspaceGoToDefinitionTest` — assert `Ctrl+B` on a local function name resolves to its declaration.
   - `XsTextMateHighlightingTest` — assert token types are assigned for keywords and strings.

**Manual smoke test:**

- Run `./gradlew runIde`.
- Open the `aom_retold_mod` project.
- Open `mod/intelligent_auto_repair_and_scout/game/ai/human_assist/human_assist.xs`.
- Verify syntax colors, completion of engine syscalls, hover on `aiPlanCreate`, parameter info inside `aiPlanAddUnitType(...)`, and go-to-definition on `disableAutoScouting`.

**No automated XS execution is required** because correctness is judged by IDE behavior, not by the game engine.

## 7. Risks & open questions

### Risks

1. **TextMate engine gaps.** The 1,626-line C++-derived grammar may use regex features or capture conventions that IntelliJ's TextMate bundle plugin handles differently than VS Code. The first verification milestone should compare highlighting of `human_assist.xs` side by side.
2. **Parser is the long pole.** Workspace go-to-definition, class member completion, and lambdas require a real PSI. If GrammarKit cannot express XS cleanly (especially `ref`, arrays, lambda types, and expression parsing), the project may need to pivot to a hand-rolled parser, adding days.
3. **XML files are inside `Data.bar`.** The AoM:R XML sources are not loose files; users must extract them. The plugin cannot auto-discover them unless it learns to read the proprietary `.bar` archive format (out of scope). The settings UI must make the paths explicit.
4. **Constants become stale across patches.** `syscalls.json`, `aiplans.json`, and any parsed XML are tied to a game version. Without the regeneration pipeline, a patch can silently break completion/hover accuracy.
5. **Doxygen defaults are not perfectly uniform.** Some functions may lack default-value tables or use different wording; the regeneration script must tolerate missing data.
6. **Rider differences.** Rider is a different IDE host. While the plugin should load, TextMate bundle registration and completion behavior must be smoke-tested in Rider specifically.
7. **Performance of 1,805 completion items.** Returning the full list on every keypress is fine if filtered by the platform, but parameter-value lookups triggered by `(`/`、` must avoid repeated JSON allocations.

### Open questions for the orchestrator/user

1. Should the plugin attempt to read XMLs directly from `Data.bar`, or is requiring extracted XML files acceptable?
2. Should XML-derived constants include the additive `*_mods.xml` files automatically, or only base files?
3. Which minimum IntelliJ Platform version should be supported (e.g., `2024.2` vs. latest stable)?
4. Should go-to-definition for syscalls open a generated stub file, or is showing documentation-only via hover sufficient?
5. Should class/lambda support be cut from Phase 2 and delivered separately if the parser becomes too complex?
6. Is the plugin allowed to include third-party Maven dependencies such as `jsoup` and an XML parser, or should it rely only on JDK and IntelliJ APIs?

## 8. Recommended sequencing

Each phase ends with a usable, manually testable plugin.

### Phase 0 — Scaffolding

- Create `tools/intellij-xs-plugin/` Gradle project.
- Register `XsFileType` and `XsLanguage` for `*.xs`.
- Bundle the TextMate grammar via `XsTextMateBundleProvider`.
- Build and run `./gradlew runIde`.

**Deliverable:** A plugin that highlights `.xs` files.

**Not yet supported:** completion, hover, go-to-definition, parameter info, XML constants.

**Verification:** Open `human_assist.xs` and confirm syntax coloring.

### Phase 1 — Engine API intelligence

- Load `syscalls.json` as a bundled resource.
- Implement `CompletionContributor` for syscall names and parameter-value completion on `(`/`.
- Implement `DocumentationProvider` for syscall hover.
- Implement `ParameterInfoHandler` for syscall parameter highlight.

**Deliverable:** A plugin with full completion/hover/parameter info for all 1,805 engine syscalls.

**Not yet supported:** workspace symbols, references, class members, XML constants.

**Verification:** In `human_assist.xs`, test `aiPlanCreate(`, hover on `kbUnitCount`, and parameter info inside `aiPlanSetVariableBool(...)`.

### Phase 2 — Minimal PSI and workspace symbols

- Build a lexer (JFlex) and a minimal parser (GrammarKit or hand-rolled) that recognizes function definitions, rules, variables, classes, and top-level identifiers.
- Implement `PsiReferenceContributor` for go-to-definition on workspace functions, rules, variables, and class types.
- Extend completion contributor to propose workspace functions and rules.

**Deliverable:** A plugin that can navigate inside the workspace and complete top-level symbols.

**Not yet supported:** class member resolution, lambdas, XML constants.

**Verification:** Ctrl+B on `disableAutoScouting` jumps to its declaration; typing `checkReservePlan` is completed.

### Phase 3 — Full PSI (classes, members, lambdas)
